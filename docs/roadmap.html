Buzzline — proposed features & where it stands

Survey of comparable tools, an honest read on the current block model, and a prioritised list of additions. November 2026.

1. Where it stands today

AreaCurrent state
What gets colouredMain prose container (reader-mode style root pick) + a 17-weight logistic block model that drops bylines, captions, citation lists and link farms. Headings and self-coloured labels are skipped.
Light / darkAlready automatic. Every scheme has a light and a dark variant; the variant is chosen per text block from the block's real computed background (nearest opaque ancestor, luminance < 0.18 ⇒ dark), falling back to the text colour. 2. Is the model trained on enough data?

Short answer: enough for 17 weights, not enough sites.

  • Samples per weight is fine. 932 labelled blocks for 17 weights ≈ 55 per weight, with L2 regularisation. A logistic model this small cannot overfit much on block count.
  • Site diversity is the real limit. 17 training sites, 11 unseen. Several features (meta, chrome, side) are class-name flags that one or two sites dominate. Leave-one-site-out shows it: Wikipedia alone drops to 0.77 precision held-out because no other training site has a reference list that looks like Wikipedia's.
  • Labels are LLM-judged, not human-judged. Spot reads found systematic noise: fully-linked teaser cards (BBC, Vox, link=1) labelled as body text. The model is partly trained toward those errors.
  • Reference point: Chrome's on-device Reading Mode model is a 241k-parameter GNN trained on ~100k labelled articles (accessibility trees). Buzzline doesn't need that, but 17 sites is two orders of magnitude thinner on layout variety.
Metric (char-weighted)Before modelWith model
Leave-one-site-out, 17 sites — precision / recall0.900 / 0.9740.953 / 0.958
11 unseen sites — precision / recall0.928 / 0.9920.982 / 0.988

Recommendation: grow to 60–100 sites / 3–5k blocks (the collector is already reusable), human-verify ~300 contested labels (anything with link ≥ 0.9 or chars < 80), and add two contextual features — "previous/next block passes" and "share of sibling blocks that are prose" — which fix most remaining short-teaser false positives without per-site rules. Keep it a single logistic layer; it is 1 ms per page and ships inline.

4. Proposed additions

P1 = fixes a visible failure or a correctness gap · P2 = clear value, moderate work · P3 = nice-to-have / investigate first

Accuracy & model

Expand the dataset + contextual features P1

60–100 sites via the existing collector, LLM labels with human verification of contested blocks, two neighbour-aware features. Target: no held-out site under 0.90 precision. Refit is node tests/e2e/train.js.

"Wrong?" feedback button → local label export P2

A tiny control in the popup: "this shouldn't be coloured" / "this should be". Stores the block's feature vector + verdict in chrome.storage.local (never text), exportable as JSON straight into tests/e2e/data. Turns every user into a labeller without telemetry.

Readability.js as a second opinion P3

Run Readability's scoring offline over the collected pages and use agreement / disagreement with the LLM judge to find label noise. Not shipped in the extension.

Score before splitting P2

Today rejected blocks are still split into char spans and then left plain. Scoring in processRoot before splitTextNode would avoid thousands of needless spans on reference-heavy pages (Wikipedia: ~80k spans).

Light / dark & colour

Contrast-guaranteed variants instead of two fixed palettes P2

Right now a block is either "light" or "dark". Mid-tone surfaces (grey cards, tinted callouts, hero images) can land both variants below WCAG 4.5:1. Proposal: keep the two anchor palettes, but nudge each colour's lightness toward the surface's opposite until contrastRatio ≥ 4.5. core.js already has contrastRatio; this is ~20 lines.

Manual override: Auto / Force light / Force dark P3

For pages whose computed background is a gradient or image (parseCssColor returns null, so detection falls back to text colour). A per-site remembered override in the popup covers the few cases auto gets wrong.

Link colour suppression (BeeLine parity) P2

Links inside prose currently keep the gradient but the page's underline/colour may fight it. Option to neutralise link colour inside coloured blocks and show links by underline only. Must not touch self-coloured status labels (already skipped).

Gradient intensity slider P3

Mix each palette toward the block's own text colour by 0–100%. Lets people who find full colour loud keep a subtle guide.

Reading features

Context-menu "Sprint selection" + keyboard shortcuts P1

contextMenus permission + commands in the manifest: right-click → Sprint, Alt+B toggle colouring, Alt+S Sprint page. Selection-aware Sprint already exists; this just exposes it where Sprint Reader users expect it.

Sprint chunking (1–3 words per flash) + per-punctuation delays P2

tokenizeWords already folds punctuation; grouping N tokens per slide and exposing the comma / period / paragraph multipliers as settings is small work in sprint.js.

Text-to-speech read-along in the Reader overlay P2

speechSynthesis is built into Chrome; highlight the paragraph being spoken. The Reader already has clean paragraphs to feed it.

Bold-prefix ("bionic") mode as an optional layer P3

Buzzline already owns a span per grapheme, so bolding the first ⌈n/3⌉ letters of each word is a CSS class flip. Worth an A/B with the reading-speed test below.

Reading-speed self-test P3

BeeLine's site sells itself with a with/without timing comparison. A one-page test in options.html (two matched passages, timed, comprehension question) gives users their own number.

Platform & performance

Firefox build P2

MV3 is supported in Firefox; the only known delta is browser.* promises vs chrome.* callbacks and checkVisibility availability. Jiffy and BeeLine both ship there.

CSS Custom Highlight API instead of char spans DONE (v0.3)

CSS.highlights + ::highlight() colours ranges without mutating the DOM, which would remove the SPA-reconciler and memory problems listed in Known limitations. Constraint: one colour per named highlight, so a gradient needs ~32 quantised highlight names per line. Prototype on one page before committing.

PDF viewer P3

pdf.js text layer is ordinary DOM; the content script could run on it with a small root rule. Large surface (Chrome's built-in viewer is not scriptable), so gate on demand.

Settings & polish

Per-site memory P2

Remember scheme, intensity and light/dark override per hostname (already keyed storage for disabledHosts; extend the shape).

Popup: live block count + "why isn't this coloured?" P3

Show the picked root and number of coloured blocks; a debug toggle that outlines rejected blocks with their model score. Would have shortened every "doesn't work here" report in this project.

5. Suggested order

  1. Dataset expansion + contextual features (the model is the thing users notice).
  2. Context menu + shortcuts (one afternoon, closes the biggest UX gap vs Sprint Reader).
  3. Contrast-guaranteed palettes (finishes the dark-mode story on mid-tone surfaces).
  4. Score-before-split (perf on heavy pages) and link colour suppression.
  5. Feedback button, Sprint chunking, TTS, Firefox.
  6. Investigate the Highlight API; everything else as demand appears.
